# Training Data Deep Dive

## 1. Overview of PersonaPlex Training Data

PersonaPlex uses **~3,467 hours** of audio across two categories:

| Category | Dialogues | Hours | Source |
|---|---|---|---|

| Synthetic (assistant) | 39,322 | 410 | LLM + TTS generated |

| **Total** | **152,035** | **~3,467** | |

## 2. Data Format at the Token Level

### 2.1 Core Tensor Format

All training data is ultimately converted to this tensor format:

```python
codes: Tensor[B, K=9, T]
```

Where:
- `B` = batch size
- `K = 9` = number of parallel token streams
  - `codes[:, 0, :]` = text tokens (Inner Monologue) from vocabulary of 32,000
  - `codes[:, 1, :]` = Mimi audio codebook 1 tokens (semantic, 2048 entries)
  - `codes[:, 2, :]` = Mimi audio codebook 2 tokens (acoustic detail, 2048 entries)
  - ...
  - `codes[:, 8, :]` = Mimi audio codebook 8 tokens (finest detail, 2048 entries)
- `T` = number of time steps at 12.5 Hz (e.g., 10 seconds = 125 steps)

### 2.2 Dual-Stream Layout

For a conversation, Moshi/PersonaPlex interleaves TWO speakers' audio:

```
Time step:        t=0    t=1    t=2    t=3    t=4    ...
─────────────────────────────────────────────────────────
Stream 0 (text):  [txt]  [txt]  [txt]  [txt]  [txt]  ... (model's inner monologue)
Stream 1 (audio): [a1]   [a1]   [a1]   [a1]   [a1]   ... (codebook 1 - user OR model)
Stream 2 (audio): [a2]   [a2]   [a2]   [a2]   [a2]   ... (codebook 2)
...
Stream 8 (audio): [a8]   [a8]   [a8]   [a8]   [a8]   ... (codebook 8)
```

But in practice, the model handles TWO separate sets of 8 audio streams:
- **User audio** (Ki streams): Input from microphone, encoded by Mimi
- **Model audio** (Ko streams): Output generated by the model

The Temporal Transformer sees the combined representation.

### 2.3 Delay Pattern

Moshi uses a **delay pattern** to handle the auto-regressive generation across codebooks:

```python
delay_offsets = [0, 0, 0, 0, 0, 0, 0, 0, 0]  # PersonaPlex default
```

The delay shifts codebook predictions in time so that:
- Text token at time t is predicted first
- Audio codebook 1 at time t is predicted using text at time t
- Audio codebook 2 at time t uses text + codebook 1 at time t
- etc.

This is implemented via `_delay_sequence()` and `_undelay_sequence()` in the code.

### 2.4 Special Tokens

```python
initial_token_id = 1024        # Audio stream start token (out of 2048 codebook)
text_initial_token_id = 32000  # Text stream start token (out of 32K vocab)
```

### 2.5 Conditioning Format (PersonaPlex addition)

Before the conversation tokens, PersonaPlex prepends:

```
[Voice Embedding Tokens] [Text Prompt Tokens] [Conversation codes[:, :, :]]
```

The voice embedding is a fixed-size tensor from Mimi encoder.
The text prompt is tokenized and placed into the text stream.

## 3. Real Data: Fisher English Corpus

### 3.1 Source

- **Fisher English Corpus Part 1** (LDC2004S13) + **Part 2** (LDC2005S13)
- 7,303 telephone conversations, each up to 10 minutes
- Two strangers having casual conversations on assigned topics
- Contains natural: stammers, overlaps, backchannels, emotional expressions

### 3.2 Processing Pipeline

```
Step 1: Raw Audio Collection
├── 7,303 conversations from Fisher Corpus
├── Two-channel audio (one channel per speaker)
├── 8kHz sample rate (telephone quality)
└── Various topics assigned to speakers

Step 2: Audio Preprocessing
├── Upsample from 8kHz → 24kHz (required by Mimi)
├── Normalize audio levels
├── Segment into manageable chunks
└── Maintain channel separation (speaker 1 vs speaker 2)

Step 3: Retrospective Prompt Annotation (KEY STEP)
├── Use GPT-OSS-120B (NVIDIA's internal LLM)
├── Analyze each conversation's content and style
├── Generate BOTH voice prompt descriptors and text prompts:
│   ├── Voice prompt: describe vocal characteristics heard
│   ├── Text prompt: describe the role/topic/context of each speaker
│   └── Both prompts follow PersonaPlex's dual-prompt format
└── This is "back-annotation" — prompts are created AFTER recording

Step 4: Audio Tokenization
├── Encode each speaker's audio with Mimi encoder
├── Produces 8 codebook token streams at 12.5 Hz per speaker
├── Extract voice embeddings from representative segments
└── Align text transcripts to generate text tokens

Step 5: Training Sample Assembly
├── Combine: [voice_prompt] + [text_prompt] + [conversation_tokens]
├── Format as codes[B, K=9, T] tensor
├── Apply delay patterns
└── Create training masks
```

### 3.3 Why Real Data Matters

Real conversations provide patterns that synthetic TTS cannot replicate:
- **Backchanneling**: "hmm", "uh-huh", "yeah", "wow" while other person speaks
- **Overlapping speech**: Both speakers talking simultaneously
- **Disfluencies**: "um", "uh", false starts, self-corrections
- **Emotional modulation**: Surprise, laughter, hesitation, enthusiasm
- **Natural turn-taking rhythms**: Variable pause lengths, interruption patterns

## 4. Synthetic Data Generation Pipeline

### 4.1 Overview

Synthetic data enables **task-following behavior** — the model learns to stay in character
and follow the text prompt instructions.

### 4.2 Step-by-Step Pipeline

```
Step 1: Scenario Design
├── Define conversation types:
│   ├── Assistant conversations (39,322 dialogues, 410 hours)
│   │   └── QA, task-oriented, information retrieval
│   └── Customer service conversations (105,410 dialogues, 1,840 hours)
│       └── Restaurant, tech support, booking, complaints, etc.
├── Create scenario templates with variables:
│   ├── Company name, product type, customer issue
│   ├── Agent personality traits, expertise level
│   └── Conversation goals and constraints
└── Define persona pairs (agent + customer)

Step 2: Text Transcript Generation
├── Use LLMs to generate conversation transcripts:
│   ├── Qwen3-32B: primary transcript generator
│   ├── GPT-OSS-120B: quality refinement and prompt generation
│   └── Multi-turn dialogue with speaker labels
├── Format: alternating turns with timing information
│   Speaker A: "Hello, how can I help you today?"
│   Speaker B: "Hi, I'm having trouble with my order..."
│   Speaker A: "I'd be happy to help. Can you give me your order number?"
│   ...
├── Generate corresponding text prompts:
│   ├── Agent prompt: "You are a customer service representative for TechCo..."
│   └── Customer prompt: "You are a customer who ordered a laptop that arrived damaged..."
└── Quality filtering: remove low-quality or unrealistic conversations

Step 3: Audio Synthesis (TTS)
├── Use Chatterbox TTS (by Resemble AI) to synthesize audio
├── For EACH speaker in the conversation:
│   ├── Select or clone a voice (different voice per speaker)
│   ├── Convert text transcript → speech audio at 24kHz
│   ├── Apply prosody variations (speed, pitch, emotion)
│   └── Generate natural pauses between turns
├── Mix two speaker audio streams with appropriate timing
│   ├── Respect turn-taking timing from transcript
│   ├── Add natural pauses (200-1000ms between turns)
│   └── Optional: add slight overlaps for naturalness
└── Output: two-channel audio (one per speaker)

Step 4: Voice Prompt Extraction
├── For each speaker, extract voice embedding:
│   ├── Take a representative 3-10 second audio clip
│   ├── Encode with Mimi encoder
│   └── Store as .pt tensor file
└── These become the voice prompts for training

Step 5: Tokenization and Assembly
├── Encode all audio with Mimi → 8 codebook token streams
├── Tokenize text prompts
├── Assemble into training format:
│   [voice_prompt_tokens] [text_prompt_tokens] [conversation_tokens]
├── Format as codes[B, K=9, T]
└── Apply delay patterns and create masks
```

### 4.3 Transcript Generation Prompt Example

```
System: You are generating a realistic customer service conversation.

Context:
- Company: TechStore Inc.
- Product: Wireless Bluetooth Headphones (Model: SoundMax Pro)
- Issue: Customer received wrong color
- Agent personality: Patient, empathetic, solution-oriented
- Resolution: Offer exchange or refund

Generate a natural multi-turn conversation between the customer service
agent and the customer. Include:
- Greeting and issue identification
- Empathetic acknowledgment
- Troubleshooting/verification
- Resolution proposal
- Closing

Format each turn as:
AGENT: <text>
CUSTOMER: <text>
```

### 4.4 Key Design Decisions

1. **Same prompt format for real and synthetic data**: Both use identical voice prompt +
   text prompt conditioning, so the model learns a unified interface
2. **Synthetic data for task-following, real data for naturalness**: The synthetic data
   teaches role adherence while Fisher data teaches natural speech patterns
3. **Diverse scenarios**: 105K+ customer service conversations cover many industries
4. **Volume ratio**: ~3:1 synthetic-to-real ratio by hours, emphasizing role control

## 5. Text Prompt Format

The text prompt has a **200-token budget** and describes the persona.

### 5.1 Structure

```
You are [role description]. [Background context]. [Behavioral guidelines].
[Scenario-specific instructions].
```

### 5.2 Examples from PersonaPlex

**Assistant role:**
```
You are a knowledgeable and friendly QA assistant. You answer questions
clearly and concisely. You ask clarifying questions when needed.
```

**Customer service role:**
```
You are a customer service representative for CloudTech Solutions.
You help customers with account issues, billing questions, and technical
problems. You are patient, empathetic, and always offer clear solutions.
The customer is calling about a billing discrepancy on their latest invoice.
```

**Casual conversation (Fisher-style):**
```
You are having a casual phone conversation with a stranger about your
favorite vacation destinations. You are enthusiastic about travel and
enjoy sharing personal stories.
```

### 5.3 Prompt Components

| Component | Purpose | Example |
|---|---|---|
| Role | Who the agent is | "customer service rep for TechCo" |
| Personality | How they behave | "patient, empathetic, professional" |
| Knowledge | What they know | "expert in cloud computing products" |
| Scenario | Current situation | "customer calling about a billing error" |
| Constraints | Behavioral limits | "do not offer discounts over 20%" |

## 6. Voice Prompt Format

### 6.1 Structure

Voice prompts are **PyTorch tensor files** (`.pt`) containing audio embeddings.

```python
# Voice prompt creation (conceptual):
import torch
from mimi import MimiEncoder

encoder = MimiEncoder.load("mimi_weights")
reference_audio = load_audio("reference_speaker.wav", sr=24000)

# Encode reference audio (3-10 seconds recommended)
voice_embedding = encoder.encode(reference_audio)

# Save as voice prompt
torch.save(voice_embedding, "voice_prompt.pt")
```

### 6.2 Pre-packaged Voices

PersonaPlex includes 16 voices:
- **Natural** (from real recordings): NATF0-3 (female), NATM0-3 (male)
- **Variety** (synthetic diversity): VARF0-4 (female), VARM0-4 (male)

### 6.3 Voice Characteristics Captured

- Fundamental frequency (pitch range)
- Speaking rate and rhythm
- Vocal timbre and quality
- Prosodic patterns (intonation contours)
- Accent/dialect features

## 7. Complete Training Sample Structure

A single training sample looks like this:

```
┌─────────────────────────────────────────────────┐
│ CONDITIONING PHASE                               │
├─────────────────────────────────────────────────┤
│ Voice Prompt: [voice_emb_1, voice_emb_2, ...]   │
│ (PyTorch tensor from Mimi encoder)               │
│                                                   │
│ Text Prompt: "You are a customer service rep..." │
│ (Tokenized to text token IDs, max 200 tokens)    │
├─────────────────────────────────────────────────┤
│ CONVERSATION PHASE                               │
├─────────────────────────────────────────────────┤
│ codes[K=9, T]:                                   │
│   Stream 0 (text):  [t1, t2, t3, ..., tT]       │
│   Stream 1 (audio): [a1_1, a1_2, ..., a1_T]     │
│   Stream 2 (audio): [a2_1, a2_2, ..., a2_T]     │
│   ...                                             │
│   Stream 8 (audio): [a8_1, a8_2, ..., a8_T]     │
│                                                   │
│ Where each column is one 80ms frame at 12.5 Hz   │
│ T = conversation_duration_seconds * 12.5          │
└─────────────────────────────────────────────────┘
```

## 8. Implications for Vietnamese Adaptation

### 8.1 What We Need to Recreate

To fine-tune PersonaPlex for Vietnamese, we need to create training data that follows
the exact same structure but with Vietnamese content:

1. **Vietnamese real conversations** (equivalent to Fisher Corpus)
   - Source: Vietnamese telephone conversations, podcast dialogues, interview recordings
   - Need: Two-speaker audio with natural interactions
   - Volume target: 500-1000+ hours minimum

2. **Vietnamese synthetic conversations** (equivalent to synthetic pipeline)
   - Use Vietnamese-capable LLMs for transcript generation (e.g., Vistral, Qwen with Vietnamese)
   - Use Vietnamese TTS for audio synthesis (e.g., VITS/ViXTTS, Resemble AI Vietnamese)
   - Create Vietnamese customer service and assistant scenarios
   - Volume target: 1000-2000+ hours

3. **Vietnamese text prompts**
   - Translate and adapt prompt templates to Vietnamese context
   - Include Vietnamese cultural scenarios (e.g., Vietnamese businesses, customs)

4. **Vietnamese voice prompts**
   - Record or collect Vietnamese speaker voice samples
   - Encode with Mimi (may need to fine-tune Mimi for Vietnamese tones)

### 8.2 Vietnamese-Specific Challenges

| Challenge | Detail | Mitigation |
|---|---|---|
| **6 tones** | Vietnamese tones carry meaning; Mimi must represent them | Fine-tune Mimi on Vietnamese audio |
| **Tonal coarticulation** | Tones change in context | Use real Vietnamese conversation data |
| **Text tokenization** | Helium tokenizer is English-focused | Extend tokenizer or use multilingual one |
| **Vietnamese diacritics** | à, á, ả, ã, ạ, ă, â, etc. | Ensure tokenizer handles full Unicode |
| **Backchanneling patterns** | Vietnamese uses different backchannel words | Include "ừ", "vâng", "à", "ờ" in data |
| **Formality levels** | Vietnamese has complex pronoun system | Reflect in text prompts and training data |
| **TTS quality** | No high-quality Vietnamese TTS matches Chatterbox | Evaluate ViXTTS, VITS, or fine-tune Chatterbox |
